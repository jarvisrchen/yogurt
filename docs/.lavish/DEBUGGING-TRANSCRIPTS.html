Where the stream forks

The load-bearing fact

The server owns the transcript. The browser never sends it back, so nothing the UI does can corrupt what is stored — a dock bug is always a rendering bug.

01

Watch the persisted transcript

Leave this running during a meeting and open the output file in an editor. It rewrites the file atomically every couple of seconds (temp file plus mv), so an editor that reloads on change never catches a half-written file.

scripts/tail-transcript.shts_ms   channel   text
# newest meeting -> /tmp/yogurt-transcript.json
scripts/tail-transcript.sh

# a specific meeting
scripts/tail-transcript.sh <meeting-id>

# somewhere else, faster
OUT=~/t.txt INTERVAL=1 scripts/tail-transcript.sh

persist_transcript writes on every final, so the file grows within a second or two of each finished utterance. If a line is in the dock but never lands here, it was a partial that never got finalized.

02

Watch the raw WebSocket

Byte-for-byte what the dock receives, partials included. Use this when you need to see partial churn — the DB tail cannot show it.

websocatsession token from ~/.yogurt/session-token
websocat "ws://localhost:7878/ws/meetings/<MEETING_ID>?token=$(cat ~/.yogurt/session-token)"

Frames are {"type":"transcript","payload":{ts_ms,channel,text,is_final}}. enhance_progress and chat frames ride the same socket, so expect other type values interleaved.

WAL mode

The database runs in WAL mode, so most GUI tools will not auto-refresh mid-meeting. Re-run the query to pick up new segments. Open read-only so you are not competing with the running server for the write lock.

Flatten the JSON column into rowsjson_each
select json_extract(value, '$.ts_ms')   as ts_ms,
       json_extract(value, '$.channel') as channel,
       json_extract(value, '$.text')    as text
from meetings, json_each(meetings.transcript_json)
where meetings.id = '<meeting-id>';

channel is "me" for mic (you) and "them" for system audio (everyone else), set by segment_json.

04

Known reasons they disagree

Work down this list before assuming a new bug. The first two are by design.

A repeated sentence appears once in the dock but twice in the DB By design

When the dock seeds itself from persisted history, it records the (channel, text) of every seeded final and drops any live final that matches. That exists to kill the duplicate you get when the history fetch races the WS subscribe.

It cannot tell a genuine verbatim repeat from a redelivery, so the DB keeps both and the dock keeps one.

web/src/lib/ws.ts:283

A line is in the dock but not in the DB By design

Almost always a partial. persist_transcript skips anything where is_final is false or the text trims to empty.

Confirm on the raw WS — if the line never arrives with is_final: true, there is nothing to persist.

crates/yogurt-server/src/meetings.rs:866

Lines are missing from both Real loss

Look for transcript persistence lagged or ws/meetings: client lagged in the server log. The broadcast channel holds 256 events; a consumer that falls behind gets a Lagged(n) and those events are gone.

Also check for the [stt overloaded, transcript may be lossy] status line, which means audio chunks were dropped upstream of STT entirely.

meetings.rs:871  ·  ws.rs Lagged branch

Timestamps restart at zero mid-meeting Bug

A stop/restart where session_offset_ms failed to resolve the original started_at. The offset is applied in exactly one place, so if the DB has it wrong the dock has it wrong too.

relay_transcript_events, meetings.rs:790

The whole prior session vanished after a restart Regression

write_segments PATCHes the entire column each time, so persist_transcript seeds its accumulator from the existing column via load_existing_segments precisely to stop this.

If it recurs, that seed is the thing to check first.

load_existing_segments, meetings.rs:899

Text renders as mojibake Not a dock bug

A storage or sanitization bug, not a rendering one. It will be identical in the tail file.
