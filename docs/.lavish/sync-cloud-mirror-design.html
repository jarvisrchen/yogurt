Yogurt Cloud: push meetings to your own Vercel and Supabase, read them on your phone

Yogurt stays a local app with no login. Yogurt Cloud is an optional mirror that you deploy yourself: a static webapp on your Vercel account, backed by a Supabase project you own. Laptops push into it and never read content back. You read on your phone after you sign in and type a 4 or 6 digit PIN. Source of truth: docs/.planning/sync-cloud-mirror-design.md.

No login to use yogurtSync stays off until you connect it in Settings.
You host itYour Vercel project and your Supabase project. Yogurt hosts nothing.
One-wayLaptops push. The webapp only reads.
A PIN gates every readPostgres checks it before any meeting is returned.
Laptops are insert-onlyA laptop can add rows and list its own meeting ids. It never reads content.
Stored readableThere is no client-side encryption. You trust the owner of the Supabase project, which is you.
Every push is keptThe cloud is an append-only history. View the library as of any earlier push.

Architecture

The webapp has no server functions. Its build applies schema.sql and writes config.json, and after that Vercel only serves files. Laptops and browsers talk to Supabase directly.

Flows

The deploy, then the four sequences, in the order you would live them.

History

Each push stores only what changed, plus a deletion marker for anything the device no longer has. The library as of push N is the latest version of each meeting at or before N.

Why not a snapshot per push

Same result, far more storage. Hourly auto-push of a 630 KB library is about 15 MB a day, which fills the free tier's 500 MB in about a month. An average version is about 14 KB, so 500 MB holds about 35,000.

Reverting is read-only

Pick a push in the webapp's History to see the library as it was. Nothing flows back to a laptop. A wiped db.sqlite marks that device's meetings deleted on the next push, and they stay readable from any earlier push.

Insert-only policies

No client can update or delete a row, and a client cannot change what a push older than one hour shows. Purging for real happens in the Supabase SQL editor.

The table is what yogurt_library(token, N) returns for each push. Push ids are global across devices, so picking a push shows every device's library at that moment.

Who can read what

Laptop secrets live in ~/.yogurt/keys.json (mode 0600), never in SQLite or a log.

Cloud loginPINCan read meetings
A laptoprefresh token in keys.jsonneverNo. It can insert, and list its own meeting ids.
A browser after unlocksessiona browser token for 12 hours or 90 daysYes
Someone with the email and passwordyesnoNo
The Supabase dashboard, its owner, or Supabase staffn/an/aYes, the data is stored readable

IT on a work laptop can take the laptop's refresh token, or the email and password if they were typed there. Either one lets them add junk rows, deletion markers, or forged meetings in new pushes. Neither lets them read a meeting, because every read needs the PIN, which is only typed into a browser. They cannot erase history, so a push from more than an hour before the damage shows the real library.

The PIN does not protect against anyone with access to the Supabase project itself. Some corporate networks block *.supabase.co or *.vercel.app, which would stop a work laptop from connecting or pushing.
